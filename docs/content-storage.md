# 详情正文无损压缩与历史去重

`content_blobs` 按原始 UTF-8 JSON 字节的 SHA-256 保存唯一正文，使用 Python 标准库 zlib level 6 压缩。采用标准库便于不同部署环境恢复；现有样本正文压缩约 78%–81%，该比例不代表整库节省比例。

`listings.payload` 保存内容引用和页面 SQL 使用的小字段投影；`snapshots.payload` 只保存引用。相同正文跨当前记录、历史版本、市场共同引用，不合并或删除观察记录。所有时间、国家、语言、状态、摘要和原始响应地址保持原值。投影保留类型、null 和缺失字段差异，筛选不需要解压正文。

数据库读取层只识别版本化的内部引用：缓冲结果按最多 100 个摘要一次读取正文，检查解压长度与 SHA-256 后返回原始 JSON。每连接解压缓存最多按 8 MiB Unicode 内存预算控制。旧的明文记录仍可读取；迁移期间两种格式并存。丢失或损坏正文会报错，不回退为不完整字段，也不自动删除历史。

页面查询不能把正文中的任意新增字段直接当成 SQL 投影字段；增加此类筛选时应同步更新 `SQL_FIELDS` 并回填投影。当前已覆盖应用分组、应用库和开发者查询的所有 SQL JSON 字段。`CAST(payload AS BINARY)` 可用于检查实际存储，正常查询和用户导出返回完整正文。

采集写入把正文、当前记录、快照和任务结果放在同一事务中。事务失败一并回滚。原始响应沿用现有 SHA-256 文件去重及 gzip 压缩策略，素材与视频保留策略不变。

## 存量迁移

先部署兼容版本到 API 和所有消费者，暂停采集，再执行：

```powershell
$env:PYTHONPATH='src'
python scripts/compact_content.py --reclaim
```

每 100 行：读取原文、核对原摘要、保存压缩正文、从数据库读回逐字节比较、替换为引用、提交断点。中断后执行同一命令续跑。先处理快照并回收物理空间，再处理当前详情；不一次复制整库。

迁移对每一行的全部元数据及原文摘要生成顺序校验链。完成后再次完整遍历，比对行数及校验链，通过后才允许在线重建回收表空间，重建后再完整校验。校验报告在 `data/exports/content-compaction-verification.json`。迁移期间不能恢复采集；手动恢复前应检查任务没有处于迁移状态。

采集的 10 GiB 保护线保持不变。压缩迁移使用独立的至少 2 GiB 工作余量检查；物理重建还要求额外的目标表与排序空间，不满足时保留已验证断点并停止。MySQL 在线重建可短暂等待元数据锁，并非无锁操作。

## 导出和备份

用户 JSONL 导出按批次还原完整正文。备份格式 3 保存物理引用和压缩二进制正文（base64 编码），恢复后校验读取仍返回原文；兼容读取旧格式 1/2。备份使用一个一致性快照，避免二次解压或存储重复正文。不要用旧版程序运行迁移后的数据库；回退须先还原为旧版可读格式，或使用匹配版本的备份。

校验不会丢弃评论、关键词、榜单或素材数据。它们当前的独立索引/观察记录保留；本次处理主要重复占用的完整应用详情正文。
